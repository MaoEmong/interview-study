1

Docker — 실행 환경을 묶는 이유

Docker는 애플리케이션과 실행에 필요한 라이브러리·설정을 Image로 묶고, 그 Image를 Container로 실행하는 도구입니다. 호스트마다 다른 환경 차이를 줄이는 것이 핵심입니다.

📐 시뮬레이터 — Image에서 Container까지
1단계 · Dockerfile은 실행 환경의 레시피파일 복사, 의존성 설치, 실행 명령을 적어 둔다. 아직 실행 중인 앱은 아니다.

VM과 Container

VM은 게스트 OS 전체를 격리하고, Container는 호스트 커널을 공유하면서 프로세스와 필요한 라이브러리를 격리합니다. 그래서 일반적으로 더 가볍고 빠릅니다.

왜 Image가 필요한가?

같은 Image를 사용하면 개발·테스트·배포 환경에서 실행 조건의 차이를 줄일 수 있습니다. Container는 Image에서 만들어지는 실행 인스턴스입니다.

Windows에서의 WSL2

WSL2는 Windows 안에서 실제 Linux 커널 기반 환경을 실행합니다. Docker Desktop과 함께 쓰면 Linux 기반 Docker Engine을 Windows에서 쉽게 사용할 수 있지만, Windows·Linux 경로 사이의 파일 I/O는 느릴 수 있습니다.

Docker Desktop은?

Windows에서 Docker Engine을 실행하고 Image·Container·Volume·Network를 관리하는 로컬 개발 도구입니다. PowerShell이나 WSL의 docker 명령과 연결되며, Desktop이 실행되어 있어야 로컬 Docker 명령이 동작합니다.

핵심: Docker의 가치는 컨테이너를 많이 띄우는 데만 있지 않습니다. 같은 Dockerfile과 Image로 실행 환경을 재현하는 데 있습니다.
2

Image·Container — 무엇을 만들고 실행하는가

Dockerfile은 Image를 만드는 명세 파일이고, docker build는 그 명세를 읽어 Image를 생성합니다. docker run은 Image를 바탕으로 Container를 만들고 실행합니다.

DockerfileFROM eclipse-temurin:17-jre WORKDIR /app COPY app.jar app.jar EXPOSE 8080 ENTRYPOINT ["java", "-jar", "app.jar"]
BASH$ docker build -t my-api:1.0 . $ docker run -d --name api -p 8080:8080 my-api:1.0 $ docker ps
명령·키워드하는 일헷갈리기 쉬운 점
docker buildDockerfile을 읽어 Image를 만든다.실행 중인 Container를 만드는 명령은 아니다.
docker runImage가 없으면 먼저 가져온 뒤 Container를 생성·실행한다.Image 자체에 상태가 저장되는 것은 아니다.
EXPOSE컨테이너가 사용하는 포트를 문서화한다.호스트에 포트를 공개하는 설정은 -p다.
CMDENTRYPOINT
기본 인자·기본 명령. docker run image 다른명령으로 대체하기 쉽다.컨테이너가 실행할 주 프로그램. 뒤에 붙은 값은 인자로 전달된다.

멀티 스테이지 빌드

빌드 도구가 필요한 단계와 실제 실행 단계를 나누어 최종 Image에는 실행에 필요한 결과물만 남기는 방식입니다.

docker commit vs Dockerfile

docker commit은 현재 상태를 임시 Image로 저장할 때 쓰고, 반복 가능한 배포에는 변경 이력이 남는 Dockerfile이 적합합니다.

종료 조건: Container는 Image와 다르게 실행 상태를 가집니다. 주 프로세스가 종료되면 Container도 종료될 수 있습니다.
3

Docker Compose — 여러 Container를 한 묶음으로

서비스가 하나일 때는 docker run으로 충분하지만, API·DB·Redis처럼 여러 Container가 함께 필요하면 Compose 파일로 네트워크·볼륨·환경변수를 한 번에 관리합니다.

📐 시뮬레이터 — Compose 내부 DNS
api → db:3306Container IP를 직접 적지 않고 Compose 서비스 이름인 db를 호스트명처럼 사용한다.
compose.yamlservices: api: build: . ports: ["8080:8080"] environment: DB_HOST: db db: image: mysql:8.0 volumes: [db-data:/var/lib/mysql] volumes: db-data:
BASH$ docker compose up -d $ docker compose ps $ docker compose logs -f api $ docker compose down

Volume

Container가 삭제·재생성되어도 DB 데이터를 보존하기 위한 저장 공간입니다. 실행 프로세스와 데이터를 분리합니다.

환경변수·설정

DB 주소나 실행 모드는 환경변수로 분리합니다. 민감한 값은 Secret, 일반 설정은 ConfigMap으로 관리하는 방향으로 이어집니다.

4

Kubernetes란 무엇인가?

Kubernetes는 여러 서버에서 Container를 관리하고 배포·확장·복구를 자동화하는 오케스트레이션 도구입니다. 사람이 Container 하나하나를 계속 확인하는 대신, 원하는 운영 상태를 적어 두고 클러스터가 그 상태를 맞추도록 합니다.

📐 클러스터의 기본 구성
YAML의 기본 축: apiVersion은 API 버전, kind는 객체 종류, metadata는 이름·라벨, spec은 원하는 실행 조건을 나타냅니다.
도구무엇을 하는가관계
Minikube로컬 PC에 Kubernetes 클러스터를 띄운다.실행할 학습 환경
kubectlAPI Server에 명령을 보내 객체를 조회·생성·수정한다.클러스터 조작 CLI
Helm여러 Kubernetes 리소스를 Chart라는 패키지로 설치·관리한다.배포 템플릿·패키지 도구

즉, Minikube는 클러스터 자체이고, kubectl은 그 클러스터에 요청을 보내는 도구입니다. Helm은 여러 YAML과 설정을 반복해서 설치해야 할 때 묶어 주는 배포 도구입니다.

5

Pod·Deployment — 실행 단위와 유지 장치

Pod는 Kubernetes가 스케줄링하는 가장 작은 배포 단위입니다. Container를 감싸며 네트워크와 저장 공간을 공유할 수 있습니다. Container와 Pod는 같은 개념이 아니지만, 실무에서는 주로 1 Pod = 1 애플리케이션 Container로 구성합니다.

📐 시뮬레이터 — Deployment가 Pod를 유지하는 방식
1단계 · Deployment가 원하는 상태를 들고 있다예: api Pod 3개, Image v2. Controller가 현재 상태와 비교할 기준이 된다.

Pod가 사라지면?

직접 만든 Pod는 사라진 채 끝날 수 있습니다. Deployment가 관리하는 Pod라면 ReplicaSet이 부족한 수를 다시 만들어 원하는 복제 수를 맞춥니다.

관찰 명령

kubectl get deployment → get replicaset → get pods -l app=api 순서로 상위 객체에서 실제 실행 인스턴스까지 내려가며 확인합니다.

BASH$ kubectl describe deployment api $ kubectl describe pod <pod-name> $ kubectl logs <pod-name> $ kubectl get pods -o wide
6

Service·Ingress — 변하는 Pod에 요청 보내기

Pod IP는 재생성될 때 바뀔 수 있습니다. Service는 라벨이 맞는 Pod들을 하나의 안정적인 접근 지점으로 묶고, Ingress는 외부 HTTP 요청을 여러 Service로 경로 라우팅합니다.

📐 요청 흐름 — 외부 요청이 Pod까지 도착하는 길
ClusterIP · 내부 서비스 주소Service가 Pod의 변하는 IP 대신 고정된 서비스 이름과 가상 IP를 제공하고, selector로 Endpoints를 찾는다.
대상역할접근 범위
ClusterIP클러스터 내부에서 Service에 접근내부
NodePort각 Node의 포트를 통해 Service에 접근외부 진입 가능
IngressHost·Path 기준으로 여러 Service에 HTTP 라우팅HTTP/HTTPS 진입점

Service Discovery와 Eureka

Kubernetes에서는 Service DNS와 selector가 기본 발견 경로입니다. Eureka 같은 별도 서비스 레지스트리가 항상 필요한 것은 아니며, 플랫폼의 네트워크 모델을 먼저 확인합니다.

Gateway와의 관계

Ingress는 클러스터 입구에서 HTTP 라우팅을 담당하고, 애플리케이션 Gateway는 인증·비즈니스 조합 등 더 높은 수준의 정책을 담당할 수 있습니다.

7

도구·운영 — 이미지를 클러스터에 전달하기

Kubernetes가 Pod를 실행하려면 Node가 가져갈 수 있는 Image가 필요합니다. 로컬에서 만든 Image를 클러스터가 볼 수 있는지, Registry 인증이 필요한지부터 확인해야 합니다.

BASH · MINIKUBE$ minikube start $ minikube image load my-api:1.0 $ kubectl apply -f deployment.yaml $ kubectl get pods $ minikube service api $ kubectl port-forward service/api 8080:80
명령언제 쓰는가
minikube start로컬 Kubernetes 클러스터를 시작한다.
minikube image load로컬 Image를 Minikube Node에서 사용할 수 있게 넣는다.
minikube service apiMinikube 환경에서 Service에 접근할 URL을 연다.
kubectl port-forward로컬 포트를 Pod·Service로 임시 연결해 빠르게 확인한다.
Image 전달의 핵심: Docker Desktop에 Image가 있다고 해서 모든 Kubernetes Node가 자동으로 보는 것은 아닙니다. 실제 클러스터의 Container Runtime과 Registry 접근 권한을 확인해야 합니다.

Rolling Update

Deployment가 새 Image 버전을 조금씩 교체해 서비스 중단을 줄이는 방식입니다. replicas, readiness, rollback 가능 여부를 함께 봅니다.

관측할 지표

Image 빌드 시간·레이어 캐시, Pod 재시작 수, Service별 replicas, 배포 중 오류율·응답 시간, 로그·메트릭 위치를 확인합니다.

🧭 장애가 나면 보는 순서

1. 객체 상태

kubectl get으로 Deployment·ReplicaSet·Pod 상태를 확인합니다.

2. 이벤트·로그

describe의 Events와 logs로 이미지·포트·프로세스 오류를 좁힙니다.

3. 네트워크

Service selector, Endpoints, targetPort, Ingress 경로를 확인합니다.

4. 실행 환경

Node의 Image 존재 여부, Runtime, Secret·ConfigMap, Volume을 확인합니다.

docker build -t my-api:1.0 . docker run -d --name api -p 8080:8080 my-api:1.0 # Kubernetes minikube start minikube image load my-api:1.0 kubectl apply -f deployment.yaml kubectl apply -f service.yaml kubectl get pods,svc kubectl port-forward service/api 8080:80

Image는 실행 환경을 담은 읽기 전용 템플릿이고, Container는 그 Image에서 만들어진 실행 인스턴스입니다.

아닙니다. Container는 프로세스 실행 단위이고 Pod는 Kubernetes의 배포 단위입니다. Pod가 하나 이상의 Container를 담을 수 있지만, 실무에서는 주로 1 Pod = 1 애플리케이션 Container로 구성합니다.

Pod를 원하는 복제 수와 버전으로 유지하고, Pod 장애 복구와 Rolling Update·Rollback을 관리하기 위해 사용합니다.

Minikube는 로컬 Kubernetes 클러스터를 실행하는 도구이고, kubectl은 API Server에 명령을 보내 그 클러스터를 조작하는 CLI입니다.

Pod IP는 바뀔 수 있으므로, Service가 안정적인 주소와 DNS를 제공하고 selector로 현재 Pod들을 찾아 요청을 전달합니다.

정의 → 필요한 이유 → 요청 또는 배포 흐름 → 주의할 점 순서로 말하면 개념과 실무 연결을 함께 보여 줄 수 있습니다.

최종 연결 문장: Docker로 서비스 실행 환경을 Image로 고정하고, Compose로 로컬 의존성을 묶은 뒤, Kubernetes의 Deployment·Service·Ingress로 복제·발견·외부 요청 흐름을 운영 환경에 맞게 관리합니다.
